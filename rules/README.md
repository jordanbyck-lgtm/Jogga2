# Rules engine

Rules are deterministic guidance that constrain the coach's recommendations. They are curated, hand-authored, and committed to the repo. They are **not** generated by the LLM at runtime.

At V1, the coach evaluates rule status by reading rule files and applying the `status_check` instruction to current `harness/` and `plan/` state. Deterministic Python computation is deferred to a later version.

---

## Tiers

| Tier | Folder | If violated |
| --- | --- | --- |
| **Hard stop** | `hard_stops/` | Coach refuses. Requires explicit athlete acknowledgment to override (and only if the rule allows it). Always logged. |
| **Strong guideline** | `strong_guidelines/` | Coach delivers the advice with a justification for the deviation. Always logged to `harness/RULES_VIOLATIONS.md`. |
| **Heuristic** | `heuristics/` | Coach delivers the advice with a one-sentence justification. Logged only if the deviation is more than incidental. |

---

## File schema

Each rule is a markdown file with YAML frontmatter:

```yaml
---
id: <unique_snake_case_id>
tier: hard_stop | strong_guideline | heuristic
statement: "<one sentence — the rule>"
evidence: "<short cite, e.g. BJSM 2025 / Daniels Running Formula / clinical practice>"
sources:
  - literature/<file>.md
applies_to:
  population: [novice, recreational, mid_level, elite, all]
  conditions: [active_injury, post_stress_fracture, ...]   # optional
computed_metric: "<what to compute>"
status_check: "<how to evaluate against current state>"
---
```

The body is markdown — discussion, edge cases, when override is acceptable, related rules.

---

## Loading

- **Hard stops** are loaded by `CLAUDE.md` at the start of every turn.
- **Strong guidelines and heuristics** are loaded on relevance: when the user message references the rule's domain (long run, intensity distribution, recovery, etc.), the coach loads matching files.

---

## Authoring new rules

Add to the appropriate tier folder. Use a descriptive `id`. Cite at least one source from `literature/` (or add the source there if it's not yet captured). Keep statements falsifiable — if you can't write a `status_check`, the rule is too vague.

---

## Known V1 limitations

- Rule status evaluation is LLM-based. The coach can be wrong. Watch for systematic failures and tighten `status_check` text accordingly.
- ACWR is intentionally NOT included. Evidence for ACWR specifically in running is conflicting; we prefer single-run progression (BJSM 2025) and weekly progression (JOSPT 2014) as primary signals.
- The "10% rule" for weekly mileage is **not** a rule here. It is a frequently cited but evidence-thin folk heuristic. The actual rules use BJSM/JOSPT thresholds.
